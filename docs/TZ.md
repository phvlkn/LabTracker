# Техническое задание
**Проект:** «LabTracker» — персональный трекер лабораторных и домашних заданий
**Редакция:** 3 (финальная), 10.09.2026
**Стек (фиксирован методичкой):** FastAPI + PostgreSQL + SQLAlchemy · React + TypeScript · Git (GitHub)

---

## 1. Назначение

Веб-приложение для учёта учебных работ студента: курсы, задания по ним (лабораторные, домашние, прочие), дедлайны, статусы выполнения и оценки. MVP отвечает на вопросы «что нужно сделать», «что просрочено», «что сдано и на сколько оценено».

### Зафиксированные решения

- Трекер персональный: пользователь видит и изменяет только свои данные.
- Типы работ: `lab` (лабораторная), `homework` (домашнее), `other` (прочее).
- Шкала оценки задаётся пользователем при создании задания (`max_grade`, по умолчанию 10); оценка — число от 0 до `max_grade` (допустима дробная с одним знаком), выставляется при создании или позже.
- Чек-листы шагов не реализуются.
- Все тексты интерфейса, README и документации — на русском языке.
- UI: библиотека **Ant Design** + сдержанная собственная тема + собственный CSS для структуры страниц; визуал простой и «авторский» (см. раздел 8).
- Репозиторий на GitHub; PostgreSQL локальный, без Docker; параметры подключения — в `.env`.
- Сводка на главном экране вычисляется на клиенте из списка заданий.

## 2. Роли и доступ

- Единственная роль — пользователь (студент), владелец своих данных.
- Публичные операции: регистрация, вход, обновление токена. Остальное — только при валидном access-токене.
- На каждом запросе к курсам/заданиям — проверка владельца; чужой или отсутствующий объект — 404/403.

## 3. Модель данных

| Сущность | Поля | Связи |
|---|---|---|
| `User` | id PK, email UNIQUE, username, password_hash, created_at | 1→M Course |
| `Course` | id PK, owner_id FK→users (ON DELETE CASCADE), title, description?, created_at | 1→M Assignment |
| `Assignment` | id PK, course_id FK→courses (ON DELETE CASCADE), title, description?, type enum(`lab`,`homework`,`other`), status enum(`not_started`,`in_progress`,`submitted`,`graded`), deadline? timestamptz, max_grade int (задаёт пользователь, default 10), grade? (0…max_grade), created_at, updated_at | принадлежит Course |
| `RefreshToken` | id PK, user_id FK→users, jti/hash токена, expires_at, revoked_at?, created_at | отзыв сессий |

### Бизнес-правила

- Удаление курса каскадно удаляет его задания; подтверждение в UI предупреждает об этом.
- «Просрочено» — вычисляемый признак: `deadline < сейчас` и статус не `submitted`/`graded`.
- Статусы изменяются свободно в любую сторону.
- Валидация оценки: 0 ≤ grade ≤ max_grade, иначе 422 с понятным сообщением.

## 4. Функциональные требования

- **FR-1 Аутентификация.** Регистрация, вход, выход. Пароли — стойким хешем (bcrypt/argon2). JWT access + refresh со сроками действия; обновление access по refresh; при выходе refresh текущей сессии отзывается; некорректный/истёкший/отозванный refresh — отказ.
- **FR-2 Курсы.** Создание, список, карточка курса с его заданиями, редактирование, удаление с подтверждением.
- **FR-3 Задания.** Создание (в т.ч. из карточки курса), просмотр, редактирование, удаление; фильтры по статусу/типу/курсу; сортировка по дедлайну; подсветка просроченных.
- **FR-4 Оценки и шкала.** `max_grade` задаётся при создании задания; оценка выставляется и правится в пределах шкалы.
- **FR-5 Сводка.** Счётчики по статусам, ближайшие дедлайны (7 дней), блок просроченных; расчёт на клиенте.
- **FR-6 Состояния интерфейса.** Загрузка, пустые состояния, ошибки сети/валидации/доступа — во всех списках и формах.

## 5. Пользовательские сценарии

1. Регистрация и вход; продление сессии через refresh; выход с отзывом сессии.
2. Создание курса «Базы данных» с описанием.
3. Создание в курсе лабораторной №2: описание, дедлайн, шкала 10 баллов.
4. Просмотр сводки: просроченные и ближайшие работы.
5. Фильтр списка заданий: «в работе» по выбранному курсу, сортировка по дедлайну.
6. Смена статуса: `in_progress` → `submitted` → `graded` с выставлением оценки в пределах шкалы.
7. Редактирование дедлайна/описания; удаление завершённого курса с подтверждением.

## 6. Экраны и маршруты

| Экран | Маршрут | Появление |
|---|---|---|
| Вход / Регистрация | `/login`, `/register` | ЛР №4 |
| Сводка | `/` | ЛР №1 |
| Список курсов + форма курса | `/courses` | ЛР №1 |
| Карточка курса с заданиями | `/courses/:id` | ЛР №1 |
| Список всех заданий с фильтрами | `/assignments` | ЛР №1 |
| Карточка задания (статус, оценка) | `/assignments/:id` | ЛР №1 |
| Форма задания create/edit | `/assignments/new`, `/assignments/:id/edit` | ЛР №1 |

## 7. Контракт API (префикс `/api`)

- `POST /auth/register` · `POST /auth/login` · `POST /auth/refresh` · `POST /auth/logout` · `GET /users/me`
- `GET|POST /courses` · `GET|PUT|DELETE /courses/{id}`
- `GET /assignments?course_id&status&type&sort` · `POST /assignments` · `GET|PATCH|DELETE /assignments/{id}`

Коды ошибок: 401 (нет/невалиден токен), 403/404 (чужой или отсутствующий объект), 409 (email занят), 422 (валидация) — с человекочитаемыми сообщениями на русском.

## 8. Нефункциональные требования

### UI и оформление

- Библиотека компонентов: Ant Design (требование методички, ЛР №1 п. 4).
- Тема через `ConfigProvider`: приглушённый основной цвет (например, graphite `#44546a`), `borderRadius: 6`, системный шрифт — без «фирменного» синего AntD.
- Используемые компоненты — только рабочие: `Button`, `Input`, `Input.TextArea`, `Select`, `DatePicker`, `Modal`, `Form`, `List`/`Table`, `Tag`, `Spin`, `Empty`. Витринные (`Steps`, `Result`, `Statistic` и т. п.) не используются.
- Структура страниц (шапка, контейнеры, карточки, сетка, отступы) — собственный CSS; визуально приложение выглядит как собранное вручную, при этом единое оформление, читаемость текста и базовая адаптивность (desktop + мобильная ширина) соблюдены.

### Репозиторий и окружение

- Структура: `frontend/`, `backend/`, `docs/` (`docs/TZ.md`, `docs/screenshots/`).
- GitHub; история коммитов регулярная, сообщения осмысленные, по этапам.
- `.gitignore` обязателен; секреты в репозиторий не попадают: только `.env.example`.
- БД: локальный PostgreSQL без Docker; в README инструкция «создать БД и пользователя → заполнить `.env` → создать таблицы».
- README на русском: назначение, сценарии, экраны, зависимости, настройка окружения, порядок запуска frontend/backend/БД, журнал существенных изменений интерфейса.

## 9. План по лабораторным и критерии приёмки

- **ЛР №1.** Каркас React+TS; роутинг всех экранов, кроме auth; демо-данные (mock); UI на AntD с темой и своим CSS; скриншоты; README с назначением, сценариями и экранами.
  *Приёмка: навигация работает, оформление едино, адаптивность не ломается.*
- **ЛР №2.** Backend: конфигурация через окружение, сессии БД, модели и связи раздела 3, CRUD-роуты раздела 7 (без auth), Pydantic-схемы с валидацией и кодами ошибок.
  *Приёмка: таблицы создаются из кода, CRUD проверен через Swagger.*
- **ЛР №3.** Слои frontend (app/pages/features/entities/shared); типизация; клиентская валидация форм; состояния загрузка/ошибка/пусто; фильтры и смена статусов на демо-данных; простые анимации (модальные окна, смена состояний).
  *Приёмка: сценарии 2–7 проходят на демо-данных.*
- **ЛР №4.** Backend-auth: хеши паролей, JWT access+refresh, ротация/отзыв, защита маршрутов, проверка владельца. Frontend: страницы входа/регистрации, хранение токенов, автопродление access, защищённые роуты, выход.
  *Приёмка: сценарий 1 проходит целиком.*
- **ЛР №5.** Замена mock на реальный API-клиент; согласование DTO; прогон сценариев 1–7 на живых данных; итоговые скриншоты и README.
  *Приёмка: демонстрация работоспособного MVP с запуском по README.*

## 10. Вне объёма MVP

Чек-листы шагов, уведомления и напоминания, календарь-сетка, вложения файлов, роли преподавателя и общий доступ, экспорт отчётов, Docker, внешний деплой.
