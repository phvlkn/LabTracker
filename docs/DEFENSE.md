# Защита лабораторных работ №1–4

## Подготовка перед защитой

Запустите PostgreSQL через Postgres.app и откройте два терминала.

Терминал 1 — backend:

```bash
cd backend
source .venv/bin/activate
python -m app.init_db
uvicorn app.main:app --reload
```

Терминал 2 — frontend:

```bash
cd frontend
npm install
npm run dev
```

Заранее откройте:

- `http://localhost:5173` — приложение;
- `http://127.0.0.1:8000/docs` — Swagger;
- редактор с проектом.

Если до этого выполнялась только команда `npm run build`, сайт ещё не запущен. Она проверяет TypeScript и создаёт папку `dist`. Для разработки используется `npm run dev`, а для просмотра собранной версии — `npm run preview`.

Перед демонстрацией полезно выполнить:

```bash
git log --oneline --decorate -8
cd frontend && npm run build
cd ../backend && source .venv/bin/activate && pytest -q
```

Так видны история этапов, успешная сборка frontend и тесты backend.

## Лабораторная работа №2 — backend, API и база данных

### Готовый текст защиты

> Цель второй работы — создать backend на FastAPI, подключить PostgreSQL через SQLAlchemy и реализовать CRUD. Точка входа сервера — объект `app` в `backend/app/main.py`, который запускается командой `uvicorn app.main:app`. При старте lifespan подготавливает схему и создаёт отсутствующие таблицы. `config.py` читает настройки из `.env`, `database.py` создаёт SQLAlchemy engine и фабрику сессий. `models.py` описывает таблицы и внешние ключи, `schemas.py` — форматы запросов и ответов Pydantic, `routers` сопоставляет HTTP-адреса с функциями, а `services.py` содержит CRUD и бизнес-проверки. На каждый запрос зависимость `get_db` выдаёт отдельную сессию и гарантированно закрывает её. Реализованы сущности Course и Assignment со связью один-ко-многим. Удаление курса каскадно удаляет задания. Pydantic и ограничения PostgreSQL не позволяют сохранить пустое название, отрицательную оценку или оценку выше максимальной.

### Путь запроса

```text
HTTP-запрос → FastAPI router → Pydantic-валидация → service
→ SQLAlchemy Session → PostgreSQL → ORM-модель → Pydantic-ответ → JSON
```

### Какие модули относятся к ЛР №2

- `backend/app/main.py` — сборка приложения;
- `backend/app/config.py` — конфигурация окружения;
- `backend/app/database.py` — подключение и сессии;
- `backend/app/models.py` — ORM-модели;
- `backend/app/schemas.py` — DTO и валидация;
- `backend/app/routers/courses.py`, `assignments.py` — CRUD-маршруты;
- `backend/app/services.py` — запросы и бизнес-логика;
- `backend/tests/test_api.py`, `test_schemas.py` — автоматические проверки.

## Лабораторная работа №3 — архитектура frontend и динамический интерфейс

### Готовый текст защиты

> Цель третьей работы — сделать интерфейс интерактивным и разделить frontend на понятные модули. Я использовал упрощённый Feature-Sliced Design. В `app` находятся сборка приложения, маршруты и глобальные providers; в `pages` — компоненты экранов; в `features` — законченные пользовательские действия, например форма задания, модальное окно курса и фильтры; в `entities` — типы и правила Course и Assignment; в `shared` — переиспользуемые компоненты, API-клиент и демонстрационные данные. Полный FSD для размера этой работы был бы избыточен, поэтому применено именно рекомендованное методичкой упрощение.
>
> После точки входа `main.tsx` корневой компонент подключает providers. `DemoDataProvider` владеет состоянием курсов и заданий и предоставляет операции добавления, изменения и удаления через React Context. После изменения React обновляет только зависящие компоненты, а эффект сохраняет данные в `localStorage`, поэтому они остаются после перезагрузки. Страницы не дублируют логику форм: они используют `AssignmentForm`, `CourseModal` и `AssignmentFilters` из features. Типы TypeScript не позволяют случайно передать несовместимые поля. Формы Ant Design проверяют обязательные поля, email, длину текста и диапазон оценки. Для экранов предусмотрены загрузка, ошибка и отсутствие данных. Добавлены короткие анимации появления и переходы наведения; при системной настройке reduced motion они отключаются.

### Откуда что берётся

- Ant Design поставляет готовые `Button`, `Form`, `Input`, `Modal`, `Select`, `Spin`, `Alert` и `Empty`;
- React предоставляет компоненты, состояние, Context, эффекты и мемоизацию;

## Лабораторная работа №4 — аутентификация и авторизация

### Готовый текст защиты

> Цель четвёртой работы — связать frontend и backend для регистрации и входа, а также защитить пользовательские ресурсы с помощью access и refresh token. Регистрация приходит в `routers/auth.py`, Pydantic проверяет email, имя и длину пароля, после чего `auth_service.py` проверяет уникальность email. Пароль никогда не сохраняется как обычный текст: `security.py` создаёт стойкий Argon2-хеш, и в PostgreSQL записывается только этот хеш. При входе введённый пароль сравнивается с хешем.
>
> После успешного входа сервер выдаёт короткоживущий JWT access token и долгоживущий случайный refresh token. Frontend сохраняет access token в `sessionStorage`, а refresh token — в `localStorage`. `AuthProvider` хранит текущего пользователя, выполняет регистрацию, вход и выход. `ProtectedRoute` не допускает неавторизованного пользователя к основным страницам. API-клиент добавляет заголовок `Authorization: Bearer <access_token>`. Если сервер отвечает `401`, клиент один раз отправляет refresh token, получает новую пару токенов и повторяет исходный запрос.
>
> На backend зависимость `get_current_user` извлекает Bearer token, проверяет подпись JWT, тип и срок действия, затем получает пользователя по `sub`. Эта зависимость подключена ко всем маршрутам курсов и заданий. Сервисы дополнительно фильтруют записи по `owner_id`, поэтому один пользователь не может читать или изменять данные другого. При обновлении refresh token применяется ротация: старый токен сразу отзывается, а клиент получает новый. При выходе refresh token текущей сессии помечается отозванным, и восстановить по нему access token уже нельзя.

### Что такое JWT

JWT — JSON Web Token, компактная строка из трёх Base64URL-частей через точку:

```text
header.payload.signature
```

- `header` сообщает алгоритм подписи, здесь `HS256`;
- `payload` содержит claims: `sub` — id пользователя, `type` — `access`, `iat` — время выдачи, `exp` — время окончания;
- `signature` создаётся из первых двух частей и серверного `SECRET_KEY`.

JWT подписан, но не зашифрован. Payload технически можно прочитать, поэтому в него нельзя класть пароль или секретные данные. Подпись нужна для обнаружения подмены. Сервер пересчитывает подпись и проверяет `exp`; изменённый или просроченный токен получает `401`.

Access token живёт 15 минут и используется часто, при каждом защищённом запросе. Refresh token живёт 7 дней и нужен только для получения новой пары. В этом проекте refresh token — криптографически случайная непрозрачная строка, а в БД хранится только её SHA-256-хеш. Поэтому утечка таблицы не раскрывает готовые refresh token. У JWT есть плюс — access token не требует отдельного запроса к таблице сессий для проверки подписи; отзыв доступа обеспечивается коротким сроком access token и отзывом/ротацией refresh token.

### Где реализована ЛР №4

Backend:

- `models.py`: `User`, `RefreshToken`, `Course.owner_id`;
- `schemas.py`: регистрация, login, token pair и user response;
- `security.py`: Argon2, создание/проверка JWT, refresh и его хеш;
- `auth_service.py`: бизнес-логика регистрации, входа, ротации и отзыва;
- `dependencies.py`: текущий пользователь из Bearer token;
- `routers/auth.py`: `/register`, `/login`, `/refresh`, `/logout`;

### Важное замечание для реального production

Для учебного MVP refresh token хранится в `localStorage`. В промышленной версии безопаснее передавать refresh token в cookie с флагами `HttpOnly`, `Secure` и подходящей политикой `SameSite`, использовать HTTPS и полноценный инструмент миграций, например Alembic.

## Короткие ответы на вероятные вопросы

**Аутентификация и авторизация — это одно и то же?** Нет. Аутентификация устанавливает, кто пользователь. Авторизация проверяет, имеет ли он право на конкретное действие или запись.

**Почему пароль нельзя расшифровать из БД?** Он не шифруется, а хешируется Argon2 с солью. При входе проверяется соответствие введённого пароля хешу.

**Почему refresh token не JWT?** Методичка требует JWT для access token. Для refresh выбран случайный непрозрачный токен: его сессию удобно хранить, ротировать и отзывать на сервере.

**Почему refresh token в БД тоже хешируется?** Если база утечёт, хеш нельзя напрямую использовать для обновления access token.

**Что произойдёт после истечения access token?** API вернёт `401`; frontend один раз обновит пару через действующий refresh token и повторит запрос.

**Что делает logout?** Клиент очищает состояние и токены, а backend отзывает refresh token текущей сессии.

**Как защищены чужие записи?** Все запросы к курсам и заданиям ограничены `owner_id` текущего пользователя. Для чужой записи возвращается `404`, чтобы не раскрывать факт её существования.

**Чем SQLAlchemy-модель отличается от Pydantic-схемы?** Модель описывает таблицу и связи в БД; схема описывает допустимый JSON на границе API.

**Почему данные заданий во frontend пока localStorage, если backend уже существует?** По методичке ЛР №3 разрешает demo-данные, а полная интеграция frontend и CRUD API является отдельной ЛР №5. В ЛР №4 реально интегрирован только сценарий авторизации.

**Зачем нужны loading, error и empty?** Асинхронные данные не всегда доступны мгновенно; пользователь должен понимать, загружается ли экран, произошла ли ошибка или записей действительно нет.

**Что такое Context provider?** Это компонент React, который хранит общее состояние и функции и делает их доступными вложенным компонентам без передачи через каждый промежуточный уровень.

**Как проверить проект?** `npm run build` проверяет TypeScript и сборку, `npm run lint` — правила frontend-кода, `pytest -q` — схемы, CRUD и безопасность backend.
